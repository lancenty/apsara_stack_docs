消息队列Kafka版的运维操作包括：

### 2.1.4. 重启Pod

本文介绍如何重启消息队列Kafka版的Pod。

**前提条件**

获取部署平台的Master节点信息。

**背景信息**

Pod不支持直接重启。当Pod状态出现异常时，建议您先通过重启进程来解决。如果重启进程后，Pod状态异常且不可恢复，您可以通过删除Pod来实现重启Pod。

**操作步骤**

1. 进入部署平台的Master节点。

2. 执行命令 `kubectl delete pod <pod>` 删除Pod。例如Pod的名称为 `alibaba-kafka-cluster-private-paas-default-0` ，则执行命令 `kubectl delete pod alibaba-kafka-cluster-private-paas-default-0` 。

### 2.1.6. 常见问题

本文介绍Pod运维过程中的常见问题。

**Pod状态为Terminating**

原因

网络插件容器故障。

措施

强制删除对应的Pod。删除后Pod会被自动调度拉起。

例如Pod为 `alibaba-kafka-cluster-private-paas-default-0` ，则执行命令 `kubectl delete pod alibaba-kafka-cluster-private-paas-default-0 -n default --force --grace-period=0` 。

**Pod状态为Pending**

可能的原因如下：

- PV资源未准备好。

- 没有合适的节点供调度。

措施

- 执行命令 `kubectl describe pod <pod>` 查看资源情况。

- 协调资源。

**Pod状态为CrashloopBackoff**

原因

通常是因为ZK的配置地址不正确引起的消息队列Kafka版进程重复重启。

措施

1. 执行命令 `kubectl describe pod <pod>` 查询日志路径。

2. 执行命令 `cd <filepath>` 切换到查询到的路径，然后查看日志文件server.log。

   > 如果无法进入Pod，您可以执行命令 `docker ps -a | grep main.*alibaba.*kafka |`
   >
   > **说明**
   >
   > `awk '{print $1}' | xargs -i docker cp {}:/home/admin/logs/alikafka/server.lo` 将日志拷贝到宿主机上进行查看。

**Pod状态为Error**

原因

通常是因为重新部署清理数据有残留。

措施

删除对应节点的物理机磁盘数据。

**broker.id出现递增导致Topic数据丢失或者不可用**

可能的原因如下：

- PV磁盘挂载之前写入错误，导致PV挂载失败。

- 清理了消息队列Kafka版资源，但是没有清理ZK数据,导致PV数据丢失。

措施

1. 执行命令 `kubectl get kafka -o yaml > new_kafka.yaml` 保留YAML文件。

2. 执行命令 `kubectl delete -f kafka.yaml` 删除消息队列Kafka版资源。

3. 执行命令 `kubectl get pvc | grep "alibaba-kafka-cluster" | awk '{print $1}' | xargs kubectl delete pvc` 删除PVC资源。

4. 检查清理结果：

   <ol type="i">

   <li>

   执行命令 `kubectl get pod | grep kafka.*cluster` 确认Pod是否清理。

   </li>

   <li>

   执行命令 `kubectl get pvc | grep kafka` 确认PVC是否清理。

   </li>

   <li>

   执行命令 `kubectl get pv | grep kafka` 确认PV是否清理。

   </li>

   </ol>

5. 删除ZK路径数据：

   <ol type="i">

   <li>

   执行命令 `kubectl exec -it zk-middleware-0 bash` 进入部署了ZK的容器。

   </li>

   <li>

   执行命令 `cd /usr/share/zookeeper/bin/` 切换到ZK的bin目录。

   </li>

   <li>

   执行命令 `sh zkCli.sh -server <zkPod`的`IP>:2188` 连接ZK。

   </li>

   <li>

   执行命令 `ls /` 列出根目录下的所有目录。

   </li>

   <li>

   执行命令 `rmr /kafka-private-clusters` 删除ZK路径数据。

   </li>

   </ol>

6. 重新部署消息队列Kafka版：

   <ol type="i">

   <li>

   删除new_kafka.yaml中的 `privileged: true` 。

   </li>

   <li>

   执行命令 `kubectl create -f new_kafka.yaml` 重新部署消息队列Kafka版。

   </li>

   </ol>

2. 执行命令 `kubectl exec -it <pod> bash` 进入部署了消息队列Kafka版的Pod。例如Pod的名称为 `alibaba-kafka-cluster-private-paas-default-0` ，则执行命令 `kubectl exec -it alibaba-kafka-cluster-private-paas-default-0 bash` 。

3. 执行命令 `sudo su admin` 切换成管理员账号。

4. 执行命令 `java -jar /home/admin/kafka-pkgs/KafkaLogChecker.jar log -g ERROR` 检查错误日志。日志返回结果为空。

## 3.4. 物理机重启后巡检

本文介绍如何在物理机重启后进行巡检。

**前提条件**

获取部署平台的Master节点信息。

**操作步骤**

1. 执行Pod状态巡检。如何执行Pod状态巡检，详情请参见 Pod状态巡检。

2. 执行业务可用性巡检。如何执行业务可用性巡检，详情请参见业务可用性巡检。

3. 进入部署平台的Master节点。

4. 执行命令 `kubectl exec -it <pod> bash` 进入部署了消息队列Kafka版的Pod。例如Pod的名称为 `alibaba-kafka-cluster-private-paas-default-0` ，则执行命令 `kubectl exec -it alibaba-kafka-cluster-private-paas-default-0 bash` 。

5. 执行命令 `cat /alidata1/kafka/kafka-logs/meta.properties | grep broker` 查看挂载数据meta.properties。挂载数据返回示例如下：

   ```text
   broker.id=1001
   ```

   > 物理机重启后，消息队列Kafka版会根据meta.properties内的ID注册3个Pod内的
   >
   > **说明**
   >
   > Broker，因此，正常情况下，Broker的ID应分别为1001、1002、1003。
